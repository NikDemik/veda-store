# Аудит модели товаров VEDA VF

Дата: 16 октября 2026. Проверены локальные `content/products/index.json`, все перечисленные в нём 929 JSON товаров, `content/series/*.json`, отчёт проверки и текущие Prisma, каталог, импорт, оформление заказа и админ-панель. Сайт-источник повторно не обходился.

## Вывод

Прежняя схема подходит для основы каталога, но не для переноса всех собранных данных без потерь. Оставлены Product, ProductType, Category, Series, AttributeDefinition, ProductAttributeValue, ProductSpec, ProductVariantGroup и ProductPackageItem. Отдельная таблица «преобразователи частоты» и новые enum для каждого вида оборудования не нужны: типы оборудования уже являются справочником ProductType.

На этапе аудита схема расширена и подготовлена отдельная SQL-миграция. По последующему запросу пользователя миграция применена к локальной БД veda_shop и загружены 929 товаров-черновиков. Ход импорта, команды и работа с файлами описаны в `docs/veda-content-import.md`. Полный интерфейс новых возможностей остаётся отдельной доработкой.

## Внесённые изменения

| Модель/поле | Назначение |
| --- | --- |
| Series.parentId | Иерархия семейств/исполнений, например VF-101 → HBC/DBC/STO/AQUA/Basic/FireMode/RPD |
| Series.description, imageUrl, sourceSnapshot | Длинное текстовое описание, основное изображение и исходный JSON серии для проверки происхождения |
| ProductSeries | Все принадлежности товара к сериям; Product.seriesId остаётся основной серией для совместимости |
| ProductOperatingRating + ProductLoadMode | Числовые powerKw/currentA по HEAVY_DUTY, LIGHT_DUTY, NO_OVERLOAD; уникальная пара productId/mode и индексы фильтрации |
| ProductSource | Исходный JSON каждой страницы, URL, время сбора и хеш HTML; уникальная тройка productId/urlHash/contentHash |
| CatalogAsset | Один физический файл по SHA-256: URL публикации, ключ хранилища, имя, MIME, размер, URL источника и время загрузки |
| SeriesDocument, SeriesImage | Связи общих файлов с сериями, порядок, подписи и группы документации |
| ProductImage/ProductDocument.assetId | Необязательные ссылки на общие физические файлы с сохранением старых полей URL |
| ProductImage/ProductDocument.inheritedFromSeriesId | Происхождение унаследованного файла; ProductDocument.group хранит раздел документации |
| ProductSpec.sortOrder, value | Порядок исходных строк и длинное текстовое значение; повторы имён допустимы |
| Product.priceOnRequest | Явное отсутствие утверждённой цены; default false сохраняет поведение старых товаров |
| URL в Product/ProductImage/ProductDocument | TEXT; ProductDocument.storageKey расширен до VARCHAR(2048), сохранив совместимый с MySQL default пустой строки |

Миграция переносит существующие ненулевые Product.seriesId в ProductSeries и задаёт старым характеристикам sortOrder по id. Старые URL/документы не удаляются и автоматически не преобразуются в CatalogAsset: их хешей в БД нет. Существующие цены не меняются, в том числе нулевые: признать их неизвестными автоматически нельзя.

Серверный `src/app/api/orders/route.ts` теперь отклоняет заказ, содержащий priceOnRequest, неактивный или непродаваемый товар. Это защищает оформление через прямой запрос и сохранённую корзину. Отображение цены по запросу в интерфейсе ещё предстоит реализовать.

## Правила будущего импорта

1. Читать только файлы из `content/products/index.json`: в папке могут оставаться материалы прежних запусков. Сначала проверить набор через `node content/verify-content.mjs`.
2. Сделать предварительный просмотр: создаваемые/обновляемые SKU, конфликты, отсутствующие цены, нераспознанные единицы, недостающие файлы. Первичная загрузка — DRAFT, публикация после проверки.
3. Подготовить справочники категорий, серий и типов. Рекомендуемые типы: частотный преобразователь, инверторный модуль, панель оператора. Типы задавать данными ProductType, не выводить весь VF-500 как один тип. Другие модули VF-400 добавлять только при наличии подтверждённых карточек: тексты серии упоминают больше оборудования, чем собрано.
4. Сохранять sku как Product.sku; model брать из подтверждённого типового кода. Пустой model допустим. Не генерировать отсутствующие характеристики пультов.
5. Product.seriesId — основная серия; ProductSeries — полный набор из seriesIds, включая основную. Старые операции записи пока изменяют только seriesId: до их доработки чтение должно учитывать основную связь и дополнительные принадлежности, а импорт — синхронизировать обе в транзакции. Проверять отсутствие циклов Series.parentId на уровне сервиса.
6. Для основной страницы и каждой sourceVariants создавать отдельный ProductSource. urlHash — SHA-256 точной source.url в UTF-8; contentHash — source.sha256. payload — полный JSON конкретного снимка, включая price, availability, characteristics, warnings, categoryPath и source.rawHtml. Одинаковые URL/хеши не дублировать. Разные снимки не сливать по принципу «последняя строка победила»; решение об опубликованных значениях принимать отдельно. Снимки могут хранить историю, Series.sourceSnapshot хранит последний импортированный исходник серии.
7. Все исходные характеристики сохранять в ProductSpec с порядком массива. Для фильтрации дополнительно заполнять ProductAttributeValue по нормализованному справочнику, не переносить туда исходные повторы. Для VF-400 создавать три ProductOperatingRating и сохранять исходные строки в specs/снимке.
8. Числа разбирать с учётом запятой/точки и пробелов, использовать Decimal и явно заданные единицы. Выходная мощность дана в кВт; powerW требует умножения на 1000. Потери, кВт — другая величина. Не путать порядок «ВхШхГ» с `Ш*Г*В`. Не выводить отсутствующее напряжение из названия без проверки.
9. Применять явное сопоставление статусов. «Под заказ» → BACKORDER; «Архивный продукт» → DISCONTINUED; временная недоступность → OUT_OF_STOCK. «На складе в Москве» не сообщает числовой остаток; не придумывать stockQty. Явное «Осталось N шт.» можно преобразовать в остаток. Условия покупки при неизвестном остатке нужно согласовать с текущей логикой витрины.
10. Проект рассчитывает заказ от цены с НДС. Числовой price.raw «без НДС» сначала преобразовать в цену с НДС по утверждённой ставке и округлить до копеек через Decimal. Исходную цену/пометку оставить в ProductSource; не считать отсутствие пометки нулевой ставкой. Не менять текущий формат цены всего проекта ради источника. Без числовой цены: priceOnRequest=true, price=0 как техническое значение, isSellable=false до реализации запроса цены в витрине. Не публиковать 0 ₽ как коммерческую цену.
11. Проверить байты/SHA-256, загрузить физический файл один раз, связать через CatalogAsset. localPath относительно content — путь для чтения, не публичный URL. При одинаковом хеше разные URL сохраняются в исходных снимках. MIME уточнять по файлу/расширению: источник отдаёт часть архивов как application/octet-stream.
12. Нормализовать названия групп документов, убирая expand_more. Создавать SeriesDocument для общих файлов. Витрина должна объединять собственные документы товара и документы всех его серий, с дедупликацией по assetId; inheritedFrom отображать как происхождение. Не копировать все общие файлы в каждый товар без необходимости. Унаследованные фотографии отмечать как изображение серии.
13. descriptionHtml хранить в исходном снимке, не выводить напрямую. Сейчас витрина использует безопасный plain text description. Для форматированного контента потребуется отдельная очистка по разрешённым тегам.
14. Импортировать пакетами с транзакциями и повторным запуском по устойчивым ключам; не удалять товары, отсутствующие в наборе. Загруженные файлы и обновления БД не образуют общую транзакцию: предусмотреть повторное использование файлов и очистку сирот после успешного завершения.

## Порядок внедрения и проверки

1. Резервная копия и применение миграции на тестовой БД той же версии, что production. Миграция содержит ALTER TABLE и перенос связей, поэтому необходимо оценить блокировки. Prisma validate подтверждает модель, но не выполнение DDL на сервере.
2. Доработать контракты API/форм и защиту черновиков, цену по запросу, файловое хранилище, JSON-импорт с предварительной проверкой. Проверить, что редактирование старой формой не стирает связи новых данных.
3. Загрузить справочники и товары как черновики, файлы — в настроенное хранилище. Пересчитать 929 уникальных SKU, 10 пересечений серий, 33 дополнительных снимка, характеристики и связи файлов. Не ожидать 952 уникальных ProductSource без проверки: повтор URL с тем же хешем дедуплицируется.
4. Проверить ABD0054: пары режимов 315 кВт/308 А, 355 кВт/394 А, 400 кВт/410 А. Проверить DBC12023 в двух сериях без второй карточки. Проверить PBN00001 без искусственных характеристик. Проверить ABN01402 без покупки по 0 ₽.
5. Проверить повторный импорт, конфликты источников, повторы «Панель оператора», длинные URL, общий файл с несколькими ссылками, крупный архив, фото серии, смену основной серии, удаление серии и сохранение редактируемых метаданных.
6. Проверить фильтры в одном режиме, пагинацию 929 товаров, серверный запрет заказа черновика/priceOnRequest/isSellable=false и расчёт НДС после конвертации цены.
7. TypeScript, production build, затем визуальная проверка витрины и админки и Lighthouse после реального наполнения.

Проверки этапа аудита: `prisma validate`, `prisma generate`, `npm run typecheck`, `npm run build` — успешно. `node prisma/verify-order-product-availability.mjs` — 6 сценариев фактического обработчика заказа с подменёнными зависимостями, без записи в БД: цена по запросу, DRAFT, ARCHIVED, isSellable=false, смешанная корзина и проход обычного товара к расчёту цены. SQL сформирован через `prisma migrate diff`. После аудита миграция применена к локальной MySQL 8.0.30; импорт и проверка данных описаны в `docs/veda-content-import.md`.
