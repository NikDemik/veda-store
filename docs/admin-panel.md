Главные пробелы для админки

<!-- Нет истории статусов заказа.
В Order есть только текущий status: schema.prisma (line 311). Для админки нужно знать, кто, когда и почему перевел заказ из NEW в IN_PROCESS, потом в PAID, и т.д.
Я бы добавил OrderStatusHistory с полями orderId, fromStatus, toStatus, changedByUserId, comment, createdAt. -->

<!-- Нет внутреннего оператора/ответственного менеджера.
User сейчас всегда привязан к Organization: schema.prisma (line 92). Это хорошо для клиентского кабинета, но плохо для админки, где нужны внутренние сотрудники: администратор, менеджер продаж, бухгалтер, закупщик.
Лучше либо добавить отдельную модель AdminUser / StaffUser, либо явно разделить пользователей на клиентских и внутренних. -->

<!-- Роли смешивают клиентские и административные смыслы.
UserRole содержит OWNER, MANAGER, ACCOUNTANT, PROCUREMENT, VIEWER: schema.prisma (line 9). Для организации-клиента это нормально. Для админки не хватает ролей вроде ADMIN, SALES_MANAGER, OPERATIONS_MANAGER, WAREHOUSE, SUPERADMIN. -->

<!-- Документы слишком минимальны.
OrderDocument хранит только тип, номер, fileUrl и дату: schema.prisma (line 353). Для операционной работы обычно нужны status, uploadedBy, fileName, mimeType, size, storageKey, signedAt, expiresAt, возможно связь не только с заказом, но и с организацией.
Также типов документов мало: нет договора, УПД/УКД, счета-фактуры, платежного поручения, спецификации. -->

<!-- Оплата и доставка смешаны с общим статусом заказа.
Сейчас один OrderStatus пытается покрыть весь процесс: schema.prisma (line 37). На практике лучше разделить:

orderStatus: новый / в работе / отменен / завершен
paymentStatus: ожидает оплаты / частично оплачен / оплачен / просрочен
fulfillmentStatus: комплектуется / отгружен / доставлен
documentStatus: документы нужны / сформированы / отправлены / подписаны
Нет полей для отгрузки.
В Order есть deliveryType, но нет транспортной компании, трек-номера, даты отгрузки, плановой даты, фактической даты доставки, стоимости доставки, контактного лица на доставку.

Нет аудита изменений.
Для админ-панели важно видеть, кто поменял клиента, адрес, цену, документ, статус, комментарий. Сейчас есть только createdAt/updatedAt. Нужна хотя бы универсальная модель AuditLog. -->

<!-- PricingRule может допускать дубли из-за nullable validFrom.
Уникальность @@unique([organizationId, productId, minQty, validFrom]): schema.prisma (line 277) в MySQL не защитит от нескольких записей с NULL в validFrom. Если это важная бизнес-логика, лучше сделать validFrom обязательным или добавить отдельный активный флаг/версионность. -->

Не хватает индексов под админские списки.

Order: [status, createdAt], [organizationId, status], [paymentType]
Organization: [fullName], [shortName], [isActive]
OrderDocument: [type, createdAt], возможно [number]
